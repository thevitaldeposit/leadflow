## 0. Done (recent)
- [x] **Pickup/asset Phase 2c — weight + overage attribute to the unit's job.** A weight now belongs to an **assignment** (unit + job), not "the lead I opened". `POST /api/leads/:id/dump-ticket` takes an optional `assignmentId`; `jobLifecycle.recordDumpTicket` resolves it first and everything after runs on **that assignment's job**: the overage prices against the size read off the **unit's asset** (so a size-changing swap bills the right allowance/rate), the ticket + invoice land on that lead/customer, and `units_out` / completion advance there — which is what fixes the **two-concurrent-jobs** bug (entering one job's ticket no longer completes another). The ticket records `size` / `assignmentId` / `assetId` / `unitLabel`, so a later weight correction re-prices against the size **that ticket** was written for. On save the assignment is stamped `weighed_at` and the can returns to `available`; a can can only be weighed once (409 — corrections go through the existing PATCH). **Yard queue** (`GET /api/assets/yard`, `components/home_services/YardQueue.jsx`, top of the Schedule page, hidden when empty): every can picked up but not yet weighed, oldest first, each with its own job — the weekend case, four cans collected Saturday and weighed over the following days, each landing on the right customer. The schedule's pickup card threads the just-picked assignment into the weight entry, and the customer profile offers the job's on-site can(s) — both resolve down the same assignment→job path. **Size write-back**: dropping a can of a different size than the job records now rewrites `vd.dumpsterSize` (preserving `dumpsterSizeOriginal`), so availability, pricing and display stop resolving against a size that isn't there; a non-size-shaped asset label can never clobber a good job size. Legacy jobs with no assignment fall through to the exact pre-2c by-lead path. Migration `assignments_weighed_at_backfill_2c` (new `migration_flags` table) closes pre-2c pickups so the queue doesn't open full of already-handled cans. Swap markers (`pendingSwapOuts` / `swapOutsApplied`), `units_out` accounting and the completion **gate** are unchanged in how they decide anything — only which job drives them. Verified **121 checks** (89 service + 32 HTTP): Fix A's paid-swap flow still keeps the job open through the first haul and completes on the final pickup **both** with and without units; two concurrent jobs complete independently; tenant isolation on the queue and the weigh action; availability byte-identical across a full drop→pickup→weigh cycle. **2d (configurable swap weight allowance) and the swap-checkbox double-arm remain.**
- [x] **Pickup/asset Phase 2b — drop/pickup capture the actual unit.** The `assignments` table created empty in 2a is now wired by `services/assignmentService.js` (`GET /api/leads/:id/units`, `POST /api/leads/:id/units/drop`, `POST /api/leads/:id/units/pickup`, all `requireAuth`). **Drop** (new action on the schedule's *delivery* card, mirroring Phase 1's pickup card — Call / Navigate / **Record drop**): the driver **must** pick a unit number — free units of the job's size first, "Different size (substitute)" opens the rest of the free fleet — which creates the assignment (`dropped_at = now`) and sets the asset `out`. The same action drops a **swap replacement** (a job can hold several open assignments at once). **Pickup**: the Phase 1 card now **requires** choosing which on-site unit came back (only that job's open assignments are offered; auto-selected when there's one), stamping `picked_up_at` and setting the asset `at_yard`; the weight / dump-ticket entry that follows is **byte-identical to before** (verified: same `unitsOut`, same `advancedTo`, same ticket shape with and without an assignment) and a job delivered before capture existed falls straight through to it. Validation: a unit can be out on **only one job at a time** (409, names the other job), a retired / out-of-service / other-tenant unit is refused, and pickup only accepts a unit actually on site. `at_yard` units are re-assignable so the yard→job→yard loop closes without a manual status flip. Assigned unit numbers show on the schedule day cards and in the customer profile's Job Details grid (read off the **booked** lead, so a later follow-up call doesn't blank it). Availability/fleet math, `units_out`, swap markers, `recordDumpTicket`, and the completion gate are untouched — verified 68 checks (service, HTTP routes, customer payload), including availability byte-identical before/after a full drop→pickup→re-drop cycle. **2c (per-unit overage attribution, swap allowance, size write-back, checkbox double-arm) remains.**
